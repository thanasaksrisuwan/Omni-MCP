# AI Agent Orchestration Protocol

**Project:** Omni-MCP: Safety-First AI Engineering System  
**Version:** 1.0.0  
**Applies To:** Gemini CLI, Codex CLI, MCP Tools, `.agent_bus/` workflow  

---

## 1. Purpose

This document defines how AI agents coordinate work in this repository.

The goal is to prevent one AI agent from doing planning, implementation, review, architecture decisions, and self-approval all by itself like a tiny software dictatorship.

This project uses an **Orchestrator-Worker** model:

```text
Gemini CLI = Architect / Reviewer
Codex CLI  = Worker / Implementer
.agent_bus = Blackboard / Audit Trail
docs/SRS.md = Source of Truth
AGENTS.md = Runtime Rules
```

Agents must communicate through files, not vague invisible chat state.

---

## 2. Core Principle

AI agents must not directly improvise implementation.

Every implementation must follow this chain:

```text
SRS
 ↓
Architect Task Spec
 ↓
Worker Implementation
 ↓
Generated Report
 ↓
Architect Review
 ↓
Approve / Revise / Reject
```

No task is considered complete until:

1. the task spec exists,
2. worker report exists,
3. generated artifacts exist,
4. validation checks pass,
5. review result is recorded.

---

## 3. Directory Structure

All orchestration runtime artifacts must be written under:

```text
.agent_bus/
├── prompts/
├── tasks/
├── reports/
├── logs/
└── reviews/
```

### 3.1 Directory Purpose

| Directory | Purpose |
|---|---|
| `.agent_bus/prompts/` | Prompt files prepared for Gemini or Codex |
| `.agent_bus/tasks/` | Task specs generated by Architect |
| `.agent_bus/reports/` | Worker execution reports |
| `.agent_bus/logs/` | stdout, stderr, git status, test logs |
| `.agent_bus/reviews/` | Architect review results |

### 3.2 Git Rule

`.agent_bus/` is runtime-only.

It must not be committed.

```gitignore
.agent_bus/
```

Because committing AI runtime chatter is how repos become archaeology sites.

## 4. Role Definitions

## 4.1 Gemini CLI: Architect / Reviewer

Gemini is responsible for:

- reading `docs/SRS.md`
- reading `AGENTS.md`
- creating strict task specifications
- identifying scope boundaries
- reviewing worker output
- detecting SRS violations
- rejecting unsafe or incomplete work

Gemini must not:

- write implementation code
- directly edit production/business logic
- expand scope beyond SRS
- modify `docs/SRS.md` to match worker output
- approve low-confidence work as safe

Gemini output should usually be one of:

```text
.agent_bus/tasks/<task_name>.md
.agent_bus/reviews/<task_name>_review.md
```

---

## 4.2 Codex CLI: Worker / Implementer

Codex is responsible for:

- reading task specs from `.agent_bus/tasks/`
- implementing only the requested scope
- adding tests and fixtures
- running tests
- generating required manifests
- writing worker reports

Codex must not:

- decide architecture independently
- expand task scope
- edit `docs/SRS.md`
- edit `AGENTS.md`
- modify business source files unless the task explicitly requires it
- claim success when tests or post-checks fail

Codex output must include:

```text
.agent_bus/reports/<task_name>_worker_report.md
```

---

## 5. Source of Truth Priority

When instructions conflict, apply this priority order:

```text
1. Safety rules in AGENTS.md
2. Requirements in docs/SRS.md
3. Current task spec in .agent_bus/tasks/
4. Implementation details inferred from code
5. Agent suggestions
```

Agent suggestions are lowest priority.  
Shocking, yes, the chatbot does not outrank the spec.

---

## 6. Task Lifecycle

Every task must follow this lifecycle.

```text
1. Architect creates task spec
2. Worker implements task
3. Worker writes report
4. Script verifies required artifacts
5. Script validates generated JSON
6. Reviewer reviews implementation
7. Reviewer returns approve / revise / reject
```

---

## 7. Task Spec Format

Architect task specs must be written as Markdown.

Required file:

```text
.agent_bus/tasks/<task_name>.md
```

Required sections:

```markdown
# Task: <task name>

## Goal
What this task must accomplish.

## Scope
What is allowed.

## Out of Scope
What must not be touched.

## Files to Create or Modify
Expected files.

## Generated Artifacts
Expected manifest/output files.

## Acceptance Criteria
Concrete pass/fail criteria.

## Commands to Run
Commands the worker should run.

## Test Fixture Requirements
Fixtures or examples needed.

## Safety Rules
Relevant SRS/AGENTS rules.

## Stop Conditions
When the worker must stop and report instead of guessing.
```

---

## 8. Worker Report Format

Worker reports must be written as Markdown.

Required file:

```text
.agent_bus/reports/<task_name>_worker_report.md
```

Required sections:

```markdown
# Worker Report: <task name>

## Summary
Short summary of what was done.

## Files Changed
List files created or modified.

## Generated Artifacts
List generated files.

## Commands Run
Commands executed.

## Test Results
Pass/fail output.

## Validation Results
JSON validation, lint, pytest, or other checks.

## Known Limitations
What the implementation does not handle.

## SRS Deviations
Any mismatch with SRS. If none, say "None".

## Follow-up Needed
What must happen next.
```

A worker report shorter than this is not acceptable.  
A 37-byte report is not a report. It is a postcard from a crime scene.

---

## 9. Review Format

Architect reviews must be written as Markdown.

Required file:

```text
.agent_bus/reviews/<task_name>_review.md
```

Required sections:

```markdown
# Review: <task name>

## Verdict
approve | revise | reject

## Blocking Issues
Issues that must be fixed before proceeding.

## Non-blocking Issues
Issues that can be fixed later.

## SRS Compliance
Whether implementation matches docs/SRS.md.

## Scope Compliance
Whether implementation stayed inside task scope.

## Artifact Check
Whether expected files exist and are valid.

## Test Check
Whether tests passed or were skipped.

## Confidence
High | Medium | Low

## Next Action
Exact next step for Codex or the human.
```

---

## 10. Verdict Rules

### 10.1 Approve

Use only when:

- task scope was followed,
- tests pass or acceptable no-test reason is recorded,
- generated artifacts exist,
- generated JSON is valid,
- SRS was not violated,
- no blocking issues remain.

### 10.2 Revise

Use when:

- implementation is mostly correct,
- blocking issues are fixable,
- scope was mostly followed,
- no unsafe production/business change occurred.

### 10.3 Reject

Use when:

- scope was expanded,
- source-of-truth files were edited improperly,
- generated artifacts are missing,
- tests were skipped without justification,
- business source files were touched unnecessarily,
- safety requirements were violated.

---

## 11. Confidence Policy

If analysis confidence is below `0.75`, the agent must not report the result as safe.

Required uncertainty format:

```json
{
  "status": "needs_manual_review",
  "risk": "unknown",
  "reason": "Explain what could not be resolved."
}
```

This applies to:

- route detection,
- dependency detection,
- session flow,
- transaction analysis,
- frontend component matching,
- prop extraction,
- design token matching,
- usage graph inference.

Unknown is not safe.  
Unknown is unknown. Amazing that we need to write this down, but here we are.

Allowed:

## 13. Day 1 Post-conditions

After Day 1 worker execution, orchestration scripts must verify:

```text
.backend-ai/index-meta.json
.backend-ai/routes.json
.backend-ai/dependencies.json
.backend-ai/validation-rules.json
.agent_bus/reports/day1_worker_report.md
```

All generated JSON files must pass:

```bash
python -m json.tool <file>
```

If any file is missing or invalid, the task fails.

No polite optimism. No “probably fine”. Computers already lie enough through exit code zero.

## 14. Day 1 Required Manifest Fields

### 14.1 `routes.json`

Each route record should include:

```json
{
  "method": "POST",
  "path": "/reservations",
  "handler": "create_reservation",
  "is_async": true,
  "source_file": "app/api/reservations.py",
  "line": 12,
  "confidence": 0.95
}
```

### 14.2 `dependencies.json`

Each dependency record should include:

```json
{
  "kind": "Depends",
  "callable": "get_session",
  "param": "session",
  "source_file": "app/api/reservations.py",
  "line": 15,
  "confidence": 0.95
}
```

For security scopes:

```json
{
  "kind": "Security",
  "callable": "get_current_user",
  "param": "user",
  "scopes": ["reservation:create"],
  "source_file": "app/api/reservations.py",
  "line": 16,
  "confidence": 0.9
}
```

```text

- Were tests run?
- Were skipped tests justified?
```

## 19. Dry-run Mode

Dry-run mode must:

1. create `.agent_bus/prompts/`,
2. ask Architect to generate a task spec,
3. write `.agent_bus/tasks/<task>.md`,
4. stop before Codex implementation.

Dry-run must not modify source files.

Example:

```bash
DRY_RUN=1 ./scripts/ai_day1_backend.sh
```

PowerShell:

```powershell
$env:DRY_RUN="1"
powershell -ExecutionPolicy Bypass -File scripts/ai_day1_backend.ps1
Remove-Item Env:DRY_RUN
```

## 21. Failure Handling

If Gemini fails:

- write stderr to `.agent_bus/logs/`,
- stop before Codex runs.

If Codex fails:

- preserve logs,
- do not run review as if implementation succeeded,
- require worker report if partial output exists.

If tests fail:

- mark task as incomplete,
- ask Codex for revision,
- do not proceed to next phase.

If JSON validation fails:

- fail task immediately.

If review verdict is `reject`:

- do not proceed,
- create a revision task.

---

## 22. Revision Protocol

When reviewer returns `revise` or `reject`, create:

```text
.agent_bus/tasks/<task_name>_revision.md
```

Revision task must include:

```text
- exact blocking issues
- files allowed to change
- files forbidden to change
- validation commands
- acceptance criteria
```

Codex must implement only the revision task.

---

## 23. Audit Trail

A completed orchestration run should leave:

```text
.agent_bus/tasks/<task>.md
.agent_bus/reports/<task>_worker_report.md
.agent_bus/reviews/<task>_review.md
.agent_bus/logs/git-status-before.txt
.agent_bus/logs/pytest.log
.agent_bus/logs/codex_worker.stdout.log
.agent_bus/logs/gemini_task.stderr.log
.agent_bus/logs/gemini_review.stderr.log
```

These files are runtime artifacts and normally ignored by git.

---

## 24. Completion Criteria

A phase is complete only when:

1. review verdict is `approve`,
2. generated artifacts exist,
3. generated JSON is valid,
4. worker report exists and is complete,
5. no blocking SRS violation exists,
6. no low-confidence result is reported as safe.

---

## 25. Final Rule

Agents must not optimize for looking successful.

Agents must optimize for producing verifiable, reviewable, bounded work.

If uncertain, stop and report:

```json
{
  "status": "needs_manual_review",
  "risk": "unknown",
  "reason": "Explain what could not be resolved."
}
```

Pretending to know is not engineering. It is cosplay with stack traces.
